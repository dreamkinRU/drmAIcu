### sync.bat: очевидный отчёт о последнем merged PR (PR #17, #19)
- После `git pull --rebase` скрипт показывает **номер и описание последнего смерженного PR**, например: «security: волна 3 — B40 тампер-детект бэкапов, B43 запрет дубликатов patch_id, B44 строгий apply_diff - #18».
- Источник: `gh pr list --state merged`; fallback без `gh` CLI — заголовок merge-коммита из `git log --grep="Merge pull request #"`.

### Оборона производителя патчей: волна 1 (PR #15)
- **B25 — path traversal через `filename`**: только `basename` + обязательное `.json` + только внутри `PATCH_DIR`; легитимная загрузка тела патча по `patch_id` сохранена.
- **B26 — атомарная запись манифеста**: tmp + `os.replace` + fsync вместо `open('w')` — сбой в момент записи больше не обрезает `patch_manifest.json`.
- **B27 — all-or-nothing бэкапы**: любая ошибка `shutil.copy2` → пустой набор бэкапов → гейтинг A-01 штатно прерывает патч.
- **B28 — hardening `safe_path`**: отклоняются пустая строка/None, backslash-сепараторы и drive-буквы Windows; **B29** — pin-тест symlink-побега.
- **B30/B31 — чистота dry-run**: `preview_patch`/`test_apply` байтно не меняют ни файлы, ни бэкапы, ни манифест.
- Тесты: 63 → 71.

### Оборона производителя патчей: волна 2 — откат и транзакции (PR #16)
- **B32 — ложный «A-02» в цепочке откатов**: rollback берёт первый timestamp-бэкап операции (не перетирается), `_LATEST.bak` — только фолбэк для legacy-записей; цепочка p4→p3→p2 больше не «застревает» на p3.
- **B39 — остатки tmp после отказа середины записи**: tmp-мусор чистится по всем запланированным целям, не только по уже записанным.
- Тесты: 71 → 81.

### Оборона производителя патчей: волна 3 — security (PR #18)
- **B40 — тампер-детект бэкапов**: в манифесте фиксируется `backup_sha` (sha контента ДО apply); при rollback вся целостность (safe_path, существование, контрольная сумма) проверяется ДО первой записи на диск. Подменённый `.bak` → откат отказывается, файл не тронут, запись в манифесте не снята.
- **B43 — запрет дубликатов `patch_id`**: повторное применение патча по `applied` отклоняется («Патч … уже применён (повторное применение запрещено)»); после rollback переприменение разрешено — штатный путь «накат → откат → накат».
- **B44 — строгий `apply_diff`**: пустой diff, текст без валидных `@@`-ханков и ханки без единой строки `-`/`+` → понятный `ValueError` ещё до транзакции.
- Тесты: 81 → 88 (`test_B40_tampered_backup_detected_on_rollback`, `test_B43_duplicate_patch_id_rejected`, `test_B44_apply_diff_rejects_garbage` и др.).

## 3.5.3 HARDENED (22.11.2026, вошла в main через PR #13)

- **Неоднозначный `search_and_replace`**: несколько вхождений подстроки → громкая ошибка вместо тихой замены первого вхождения (B20).
- **`expected_sha`**: опциональное поле операции; SHA-256 файла на момент начала патча; несовпадение отвергает патч целиком.
- **Re-check диска**: между расчётом и записью диск перечитывается и сверяется с базовым SHA (B21).
- **`TX_LOCK`**: `apply_patch` и `rollback` сериализуются RLock'ом (B24); `get_engine` снова инициализируется внутри лока.
- **Путь к `tscheck.cjs`** вычисляется от `main.py`, а не от `BASE` (фикс для pytest с `tmp_path`).
- **Безопасность**: `/api/patches/delete` и `/api/patches/archive` — `os.path.basename` + обязательное `.json` (B22); CORS `allow_origins` вместо `*`; Vite dev-server слушает `127.0.0.1`.
- **Роуты**: `/api/patches/stats` больше не перекрыт `s_pvalidate_all` (B23).

## 3.5.2 HARDENED (19.11.2026, патчи 080–082)

- **Замок транзакций** (тогда `PATCH_LOCK`, ныне `TX_LOCK`): одна транзакция одновременно, защита от двойного клика (B12).
- **Детект устаревшего кода** (тогда `MAIN_HASH` — хеш `main.py`, ныне per-file SHA и `expected_sha`): отказ при изменении кода на диске вне панели (B19).
- **Идемпотентность `search_and_replace`** (B17): замена уже применена → операция возвращает содержимое без изменений.
- **Ротация манифеста** (B14): последние 100 записей `applied` / 500 `history` вместо бесконечного роста.
- **1 бэкап + ротация 10** (B16): имя по относительному пути с микросекундами (`src__App.tsx_<ts>.bak`) вместо тройного бэкапа.
- **Накопление операций** (B18): `compute_ops` складывает последовательные операции в кэше — 20 операций над одним файлом дают 1 запись и 1 бэкап.
- **Диф-движок** (B1–B5): хвостовой `\n` не создаёт фантомную пустую строку; CRLF не внедряет `\r`; вставка `-N,0` вставляет после строки; тихий пропуск ханков заменён ошибкой.
- **Валидация перед записью** (B8): `ast.parse` для Python, `json.loads` для JSON, `tsc` (`tscheck.cjs`) для TS/TSX.
- **Песочница путей** (B9): `../` и абсолютные пути отклоняются. **Байтовый SHA-256 и сохранение переносов строк** (B11).
