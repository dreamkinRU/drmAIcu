# Storage Contract drmAIcu v1.0

**Статус:** нормативный контракт для новых и изменяемых persistence-компонентов. Наличие этого документа само по себе не означает, что все legacy-файлы уже мигрированы.

## 1. Цели

- Не превращать повреждённое или недоступное хранилище в пустое состояние.
- Не подтверждать успешную запись до завершения атомарной замены и flush данных.
- Сохранять совместимость с legacy-форматами через явные миграции.
- Делать сбой, деградацию и необходимость восстановления видимыми для UI и диагностики.
- Не смешивать секреты с журналами, экспортами и обычными диагностическими ответами.

## 2. Контракт JSON-хранилища

Каждый новый JSON-документ состояния обязан иметь schema_version и валидируемую корневую структуру. Для уже существующих файлов без версии применяется legacy reader; добавление версии выполняется миграцией, а не молчаливой перезаписью при чтении.

Запись выполняется по схеме: сериализация в соседний временный файл → flush → fsync → os.replace. Временный файл удаляется только после безопасного определения, что он не является частью незавершённой операции. Для важных данных ошибка записи должна возвращаться вызывающему коду и отражаться как persist_error.

## 3. Контракт транзакций

- Одна запись файла может быть атомарно заменена через os.replace на поддерживаемой файловой системе.
- Набор нескольких файлов не является атомарным для внешних читателей без дополнительного поколения/manifest pointer.
- Multi-file операции обязаны иметь durable journal до первой целевой записи, идентификатор операции, список целей, исходные контрольные суммы, сведения о восстановлении и явный commit marker.
- После аварии recovery выполняется до новых операций записи (recovery barrier).
- Повреждённый, неизвестный или недоступный journal означает RECOVERY_REQUIRED; автоматическое удаление и старт «с чистого листа» запрещены.
- Частичное восстановление остаётся заблокированным и требует диагностики; нельзя выдавать его за успех.

## 4. Конкурентный доступ

In-process lock защищает только потоки одного процесса. Для межпроцессной координации используется advisory lock с понятным scope и timeout. Внешние приложения не обязаны соблюдать advisory lock; поэтому критические операции дополнительно проверяют version/snapshot до и после commit. Для данных, которые должны быть изолированы от произвольных внешних writers, требуется отдельный storage protocol или OS-level locking.

Lock registry должен иметь ограниченный жизненный цикл и не удерживать бесконечно ключи завершённых ресурсов. Нельзя удалять активный lock без синхронизации с ожидающими потоками.

## 5. Ошибки и деградация

Persistence API различает как минимум состояния OK, UNAVAILABLE, CORRUPT, RECOVERY_REQUIRED и WRITE_FAILED. UNAVAILABLE и CORRUPT не трактуются как пустое хранилище. Деградированное состояние может продолжать обслуживать чтение из памяти только при явной диагностике и без заявления, что данные сохранены на диск.

## 6. Секреты и журналы

Секреты хранятся отдельно от обычных настроек и activity logs. В логах допустимы только имена ключей и факт операции; значения, bearer tokens, URL userinfo и credential query parameters должны редактироваться до записи и до выдачи наружу.

## 7. Миграции и обратная совместимость

Миграция обязана:
1. Проверить исходную схему и версию.
2. Создать резервную копию или recovery snapshot.
3. Преобразовать данные во временный файл.
4. Проверить результат новой схемой.
5. Заменить исходный файл атомарно.
6. Сохранить диагностический след и не удалять исходник при ошибке.

Неизвестная будущая schema_version означает отказ от записи, а не downgrade.

## 8. Текущая карта и миграционный долг

| Хранилище | Текущий владелец | Требование контракта / статус |
|---|---|---|
| patch_manifest.json | patch_engine.py | Валидация структуры и блокировка повреждённого манифеста уже реализованы; schema version — отдельная миграция |
| patch_journal.json | patch_engine.py | Durable journal, recovery barrier и fail-closed поведение при повреждении реализуются в hardening PR |
| data/plugins/registry.json | core/plugins/registry.py | Atomic persistence и memory degradation; schema version / миграции — долг |
| data/plugins/permissions.json | core/plugins/permissions.py | Legacy JSON persistence; требуется отдельная миграция |
| data/plugins/confirmations.json | core/plugins/confirmations.py | TTL/single-use semantics; schema version / recovery contract — долг |
| data/plugins/state/ | Settings / plugin state | Отдельные файлы; единая схема миграций — долг |
| data/plugins/secrets/ | core/plugins/secrets.py | Изолированное хранение; schema version и backup policy не должны раскрывать значения |
| data/plugins/activity/*.jsonl | core/plugins/events.py | Append-only журнал; ротация/повреждённая последняя запись требуют отдельной политики |
| settings.json, provider config, project history | main.py и сервисы | Legacy persistence; постепенно перевести на общий контракт без массового переписывания |

## 9. Тестовые требования

Каждый изменяемый storage-компонент получает fault-injection tests для: обрыва до temp write, обрыва после fsync, ошибки replace, повреждённого JSON, неизвестной версии, недоступного файла, параллельной записи и восстановления после незавершённой транзакции.

Проверка должна подтверждать не только итоговый файл, но и статус/диагностику, отсутствие ложного успеха и сохранность исходных данных.
