# Update Manager — мастер обновления drmAIcu

**Статус:** реализуется в отдельной ветке `feature/update-wizard-three-step`.  
**Назначение:** обновить установленный Git checkout из официального репозитория, не смешивая этот процесс с пользовательской синхронизацией Repos Plugin.

## Три этапа

### 1. Проверка и план

- Определяет текущую ветку, upstream, HEAD и состояние рабочей директории.
- Проверяет, что upstream указывает на официальный HTTPS-репозиторий `github.com/dreamkinRU/drmAIcu`.
- Выполняет `git fetch --no-tags` только для получения удалённых объектов и refs. Рабочие файлы не меняются.
- Показывает ahead/behind, входящие коммиты, локальные изменения и список файлов, которые придут с обновлением.
- Обнаруживает локальные коммиты поверх upstream, изменения package manifest без lock-файла, а также файлы миграций. Такие случаи блокируют автоматическое применение.
- Создаёт план с UUID и fingerprint рабочего дерева. Fingerprint включает staged diff, unstaged diff и содержимое untracked-файлов. Изменение файлов после проверки делает план недействительным.

### 2. Резервирование и обновление исходников

После отдельного подтверждения:

1. Повторно проверяет HEAD и fingerprint.
2. Если есть локальные изменения, создаёт Git stash с `--include-untracked`. Игнорируемые файлы не очищаются.
3. Создаёт независимую ссылку `refs/drmaicu/update-backups/<operation-id>` на stash-коммит и проверяет, что объект доступен.
4. Проверяет чистоту рабочей директории.
5. Выполняет только `git merge --ff-only <target-sha>`.
6. Сверяет фактический HEAD с целевым SHA.

Update Manager не вызывает `git add`, `commit`, `push`, `pull --rebase`, `stash drop` или `reset --hard`. Он не удаляет резервные refs автоматически.

### 3. Восстановление и подготовка окружения

- Восстанавливает stash через `git stash apply --index <backup-ref>`: отдельно сохраняется исходное staged/unstaged состояние.
- При конфликте останавливается, не удаляет backup и переводит операцию в состояние восстановления.
- Пользователь может разрешить конфликт вручную и явно подтвердить завершение восстановления.
- `requirements.txt` изменился → `python -m pip install -r requirements.txt`.
- `package-lock.json` изменился → `npm ci`.
- Изменился frontend-код/конфигурация → `npm run build`.
- Миграции БД не запускаются автоматически: их наличие блокирует обновление до отдельной проверки.
- Если изменён Python-код или requirements, мастер переходит в `RESTART_REQUIRED`. Он не завершает процесс автоматически. После ручного перезапуска новый PID подтверждается при следующем запросе состояния.

## Журнал и восстановление

Журнал находится в `data/updater/journal.json`, записывается через временный файл + `os.replace` и сохраняет этап, HEAD, backup ref, сведения о bundle, результаты окружения и ошибки. Каталог `data/updater/` исключён из Git. Повреждённый журнал и оставшийся после аварии `.tmp` блокируют продолжение.

Основные состояния:

- `IDLE` — операция не начата.
- `CHECKED` — план проверен, ожидается подтверждение.
- `APPLYING` — выполняется резервирование/fast-forward.
- `CODE_UPDATED` — исходники обновлены, ожидается восстановление и окружение.
- `RESTORING` — выполняется восстановление локальных изменений.
- `RESTART_REQUIRED` — файлы/зависимости обновлены, но процесс ещё не перезапущен. При следующем обращении к API из нового PID мастер подтвердит перезапуск и переведёт операцию в `COMPLETED`.
- `COMPLETED` — шаги мастера завершены, а обязательный перезапуск подтверждён (если он требовался).
- `FAILED` — обновление не применено; можно выполнить новую проверку.
- `PREPARING` — восстанавливаются зависимости и выполняется frontend build.
- `RECOVERY_REQUIRED` / `UPDATE_NEEDS_REPAIR` — нужна операция восстановления.

Повторная операция блокируется, пока предыдущая не завершена или не переведена в безопасное состояние. Backup ref и bundle остаются доступны даже после успешного восстановления — их удаление не входит в автоматический процесс.

## API

- `GET /api/updates/state`
- `POST /api/updates/check`
- `POST /api/updates/apply` с `operation_id`
- `POST /api/updates/prepare` с `operation_id`
- `POST /api/updates/recover` с `operation_id`; `manual_confirmation: true` — явное подтверждение ручного восстановления.

Изменяющие endpoint-ы проверяют loopback Origin, Host и client address. Это CSRF/browser-origin барьер, а не аутентификация против другого локального процесса под той же учётной записью ОС.

## Ограничения первой версии

- Требуется Git checkout с upstream и официальным HTTPS remote.
- Ветки с локальными коммитами ahead, diverged history и миграциями блокируются.
- Изменения submodule не резервируются автоматически и блокируются.
- Игнорируемые файлы не включаются в backup и не удаляются.
- Не выполняется автоматический rollback установленных Python/npm-пакетов: восстановление Git-кода не гарантирует обратимость side effects установщиков.
- Проверка успешного HTTP-ответа API подтверждает работоспособность текущего процесса на момент вызова, но после изменения Python-кода требуется его перезапуск для загрузки новой версии.
- Update Manager не является системой обновления для архива без `.git` и не предназначен для обновления сторонних репозиториев.
