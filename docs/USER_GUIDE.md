# Руководство пользователя drmAIcu

**Версия 3.19.2 Model** · Обновлено: 27.11.2026 · Включает PR #10–#63 и патчи 144–162

## Быстрый старт
1. Запусти `launcher.bat` (он автоматически убьёт зависшие процессы, запустит ядро + UI и один раз откроет браузер).
2. Открой http://127.0.0.1:5173 в браузере.
3. Для теста: `python -m pytest tests -q` (ожидаемо **300 passed, 1 skipped**: движок патчей + система плагинов + гигиена MD + плагин Репозитории).

## Основные вкладки

### 🖥 Консоль
- Кликни по названию провайдера или модели в верхней строке консоли, чтобы быстро выбрать сервер (**Ollama**, **Strata**, **LM Studio**, **Bionic**, **Groq** или **Все**) и нужную модель.
- Напиши запрос и нажми `Enter` для отправки (`Shift+Enter` — перенос строки).
- В поле отправляется только новый введённый текст после последнего ответа, что защищает локальные модели от зацикливания; тройные кавычки и лишние пустые строки очищаются автоматически.
- Во время генерации доступна кнопка ⏹ **Стоп** (отмена SSE-потока), после завершения — ↻ **Повторить** и 🗑 **Очистить**.
- В правом верхнем углу отображается телеметрия последнего ответа: скорость (`tok/s`), общее время, время первого токена (`TTFT`) и объём в токенах.

### 🌐 Провайдеры (единый центр подключений и моделей)
- Объединяет настройки серверов и выбор моделей в формате **Master–Detail**:
  - **Левая колонка**: список всех локальных и облачных провайдеров (**Ollama**, **Strata**, **LM Studio**, **Bionic AI**, **Groq**, **OpenRouter**, **Together AI**, **Hugging Face**, **Gemini**) с живым автообновлением статусов каждые 5 секунд (**Онлайн** / **Оффлайн** / **Выкл**) и тумблерами активности.
  - **Правая колонка — «Подключение и статус»**: поля для хоста/URL, порта и API-ключа (с кнопкой просмотра), переключатель включения и кнопки 🔍 **Проверить** / 💾 **Сохранить** (сохраняет параметры в `localStorage` и `config.json`).
  - **Правая колонка — «Доступные модели»**: список моделей выбранного провайдера (для локальных серверов `embed`-модели скрыты автоматически) с кнопкой **«Выбрать»** / индикатором **«Активна»**. Для **Ollama** также доступно поле скачивания новых моделей (`ollama pull`).

### 🔄 Патчи (PATCHMASTER)
- ИИ генерирует JSON-патч. Сохрани его в папку `patch/` или в системную папку `Загрузки` — панель обнаружит его автоматически и покажет всплывающее окно с кнопкой **«Применить»** (после применения автоматически вернёт на исходную вкладку).
- Кнопка 👁️ **Просмотр** — сухая проверка без записи на диск.
- Кнопка ✅ **Применить** — атомарная запись с бэкапом, автопереносом применённого патча в `patch/archive/` и тихим автоперезапуском панели (с бейджем в правом нижнем углу), если патч затронул `.py`-файлы.
- **Мульти-патчи**: один JSON обновляет несколько файлов через массив `operations`.
- Кнопка ↩ **Откатить** — восстанавливает последний применённый патч из бэкапа.
- Кнопка 📦 **Архив** — перемещает патч в `patch/archive/`.
- Кнопка ⚡ **Применить все** — массовое применение ожидающих патчей.
- **Preflight**: перед применением фаза 1 транзакции проверяет, что каждый `find` встречается в файле ровно 1 раз, а `expected_sha` (если задан) совпадает с состоянием на диске — иначе весь патч отвергается.

### 🗂 Файлы (Умная очистка)
- Нажми 🧹 **Режим очистки**.
- Система проанализирует все файлы и подсветит:
  - 🔴 Красным: безопасные для удаления (пустые, кэш, старые версии `_vX`, `_fixed`, `_ru`).
  - 🟡 Жёлтым: требующие проверки (большие логи, дубликаты).
- Нажми 🗑 **Удалить X файлов** — они перемещаются в `project_archive/` с датой.
- Переключатели категорий: критичные / важные / мусор / дубликаты.
- Поиск и фильтры по категории, имени, дубликатам, превью файла (кнопка 👁), защита важных файлов звёздочкой и архивация (кнопка 📦).
- Позиция прокрутки сохраняется при обновлении списка; кнопка 🔄 **Пересканировать** обновляет анализ.

### ⚙️ Шапка, подвал и остальные вкладки
- **Шапка**: компактная однострочная навигация с подсветкой активной вкладки и счётчиками по разделам (**Агенты**, **Провайдеры**, **Файлы**, **Патчи**, **Код**, **Задачи**, **MD**).
- **Подвал**: слева быстрый доступ к **Логам**, справа — капсулы **RAM** и **VRAM** с визуальной шкалой заполнения памяти в реальном времени и кнопка **Перезапуск** (перезапускает Python и React через `restart.flag` без открытия новой вкладки браузера).
- **Агенты**: включение/выключение, прогресс, магазин агентов.
- **Код**: список найденных проблем с кнопкой «Исправить».
- **Задачи**: добавление с приоритетом и категорией, отметка выполнения, удаление.
- **MD**: редактор Markdown-документации прямо из панели.
- **Логи**: просмотр логов ядра в реальном времени.
- Порт фронтенда **5173**, порт ядра **8080**. Прокси `/api` настроен в `vite.config.js`.

## Формат мультифайлового патча
```json
{
  "patch_id": "161",
  "type": "multi",
  "description": "Описание изменений",
  "operations": [
    {"type": "full_replace", "target_file": "file1.md", "full_file_content": "..."},
    {"type": "unified_diff", "target_file": "file2.py", "diff": "..."},
    {"type": "search_and_replace", "target_file": "file3.tsx", "find": "старый_текст", "replace": "новый_текст"},
    {"type": "create", "target_file": "new_file.tsx", "full_file_content": "..."}
  ]
}
```

## Типы операций
- **`full_replace`** — полная замена файла. Надёжна, не зависит от текущего содержимого. Идеальна для документации и крупных правок.
- **`unified_diff`** — точечные вставки/удаления по контексту. Поиск по содержимому, а не по номерам строк.
- **`search_and_replace`** — замена подстроки. Автоматически нормализует переносы строк (CRLF ↔ LF). Идемпотентна в 3.5.2+.
- **`create`** — создание нового файла. Отказывается, если файл уже существует.
- **`expected_sha`** (опциональное поле) — защита от перезаписи из устаревшей вкладки.
- **`backups`** — автоматически создаётся 1 бэкап с ротацией последних 10.
- **`rollback`** — восстановление последнего патча из бэкапа.

## Безопасность и надёжность
- **Идемпотентность**: повторное применение `search_and_replace` безопасно — если замена уже есть, операция возвращает содержимое без изменений.
- **Замок от двойного клика**: одновременное применение двух патчей отклоняется.
- **Детект устаревшего кода**: если целевой файл изменился на диске вне панели, применение патчей блокируется с понятной ошибкой.
- **`expected_sha`**: задайте хеш файла в операции, чтобы защититься от перезаписи из устаревшей вкладки браузера.
- **Накопление операций**: 20 операций над одним файлом складываются корректно, а не перезаписывают друг друга.
- **Ротация манифеста**: `patch_manifest.json` хранит последние 100 применённых / 500 истории.
- **1 бэкап + ротация 10**: вместо тройного бэкапа — экономия дискового пространства.
- **Двухфазный атомарный коммит**: либо все файлы, либо ничего.
- **Валидация перед записью**: `ast.parse` для Python, `json.loads` для JSON, `tsc`/`tscheck.cjs` для TS/TSX.
- **Песочница путей**: `../` и абсолютные пути в операциях отклоняются.
- **Автооткат**: при несовпадении контрольной суммы файлы восстанавливаются из бэкапов.

## Типовые ошибки и пути исправления

### «Отказано в доступе» / [WinError 5] при записи данных панели (sync с изменениями)

- **Симптом**: `[WinError 5] Отказано в доступе: '...data/plugins/confirmations.json.tmp' -> '...confirmations.json'` во время синхронизации. Появляется при нагрузке на диск (создаётся много файлов — git + антивирус + облако), поэтому чаще при синхронизации С изменениями.
- **Причина честно**: файлы состояния панели (`data/plugins/*.json`) перезаписываются атомарно (`.tmp` → переименование). Windows запрещает переименование, если целевой файл в этот момент держит другая программа: антивирус, индексатор или облачная синхронизация (папка в G:\Mega\ — клиент Mega), успевшая открыть только что созданный `.tmp`.
- **Что уже сделано в панели**: панель сама делает до 10 повторных попыток с паузами (~3,5 с суммарно) — кратковременные блокировки проходят незаметно.
- **Путь исправления**: если после 10 попыток ошибка всё же видна — закройте/приостановите программы, удерживающие файлы (антивирусный скан, Mega/OneDrive/Dropbox синхронизацию на время коммита), запустите панель от имени владельца папки. Ошибка не теряется: она остаётся в липкой плашке и во вкладке «Логи».

### Кнопка «Очистить ошибки» во вкладке «Логи»

- Ошибки и предупреждения не исчезают сами (прилепают), но и не должны висеть вечно: кнопка «✕ Очистить ошибки (N)» удаляет из журнала записи уровней error/warn — и из ядра (`/api/logs`), и из журналов активности плагинов (`data/plugins/activity/*.jsonl`). Info-записи и действия остаются.
- Путь исправления (если кнопка не активна): кнопка отключена, пока ошибок нет (счётчик 0).


### «есть незакоммиченные изменения — требуется сообщение коммита» (кнопка Синхронизировать)
- **Причина**: в репозитории есть незакоммиченные изменения, а для авто-коммита в Синхронизации (как и в sync.bat) пустое сообщение отклоняется.
- **Исправление**: введите сообщение коммита в поле над кнопкой «Синхронизировать» (или в разделе «Изменения» → «Коммит (по шагам)») и повторите — sync сам выполнит add -A → commit → pull --rebase → push. Список того, что уйдёт в коммит — в этой же вкладке, блок «Файлы с изменениями в этом репозитории».

### Диалог перед синхронизацией с локальными изменениями (с 3.12.4)
- Перед Sync сначала показывается предпросмотр: полный diff всех staged, unstaged и новых файлов, список файлов, stat. Никакие файлы не индексируются и не коммитятся до отдельного подтверждения WRITE. Этапы: «Предпросмотр Sync» → проверка diff → «Перейти к подтверждению WRITE» → approve в жёлтой плашке. Это защита от случайного коммита — изменения уйдут в удалённый репозиторий только после подтверждения.
- При наличии изменённых файлов пустое сообщение коммита блокирует продолжение (sync.bat отклоняет пустое сообщение при изменениях) — укажите сообщение в поле над кнопкой до подтверждения.
- Если preview обрезан по лимиту (неполный), требуется явный чекбокс-подтверждение перед продолжением.
- Если синхронизация прервалась ошибкой, над пошаговым журналом появляется отдельный красный блок с полным текстом ошибки и «Путём исправления» (переносы строк сохранены). Ошибка также остаётся во вкладке «Логи» — «confirmation_required» в логах это НЕ ошибка, а штатное ожидание вашего подтверждения WRITE-операции.
- Вкладка «История»: клик по строке коммита открывает модальное окно деталей (тема, sha, дата и время HH:MM (UTC+3), полное тело коммита; Escape/✕/клик по фону закрывают); мерж-коммиты не занимают отдельных строк — блок «Этот коммит вошёл в ветку через мердж» виден в том же окне. Текущий репозиторий с путём — под заголовком «📁 Репозитории» и в ⚙ Настройках.
- Preview Sync (с 3.12.7) показывает и ЛОКАЛЬНЫЕ изменения (файлы + diff), и то, что придёт с remote: сначала выполняется git fetch, в заголовке — счётчики «↑N на отправку · ↓M с remote», ниже список входящих коммитов «Придёт с remote». Если fetch не удался (сеть/доступ), появится предупреждение с путём исправления, а счётчики могут быть неточными.
- **«Актуально» после Sync (с 3.13.0)** — при успехе панель показывает зелёный итог «Актуально: локальная копия = GitHub» с веткой и HEAD, что отправлено (commit) и сколько коммитов получено с remote (список sha + тема); если с remote ничего не пришло — так и написано.
- **Проект в облачной папке (Mega/OneDrive/Dropbox) (с 3.13.0)** — облачный клиент удерживает файлы состояния (`data/plugins/registry.json` и др.) и вызывает ошибку `[WinError 5]`. Панель переживает это: состояние живёт в памяти, во вкладке «Плагины» появляется янтарный баннер деградации с текстом ошибки и путём исправления. Рекомендация: добавьте папку `data/` в исключения облачной синхронизации (Mega → Настройки → Игнорируемые файлы) или перенесите проект из синхронизируемой папки. Также: Sync обновляет исходники, но фронтенд нужно пересобрать (`npm run build` или start.bat) — иначе в шапке остаётся старая версия.
- Самопроверка плагина Репозитории при старте (с 3.13.1): если после прервавшейся синхронизации файлы плагина разноверсионные, плагин не запускается и показывает одну понятную ошибку с путём исправления вместо потока capability_failed в логах.
- **Версия в шапке (с 3.12.9)** — оболочка показывает `v.X.Y.Z Model` из `version.py` через API `/api/version`: версия в UI всегда совпадает с фактической версией кода, застарелый хардкод «3.6.1» устранён.
- Интеграция PATCHMASTER (с 3.12.8): если AI-патчи применены движком, но ещё не закоммичены, во вкладке «Репозитории» показывается янтарный баннер со списком файлов и путём исправления (Предпросмотр Sync → сообщение коммита → Синхронизировать). Красные баннеры: незавершённая транзакция патча (перезапустите панель — ядро откатит по crash-журналу) и заблокированный движок (восстановите patch_manifest.json из .corrupt-копии). Сам плагин файлы не пишет — запись исходников остаётся у PATCHMASTER.
- Результат Sync всегда виден (с 3.12.5): над пошаговым журналом — постоянный заголовок. Успех: «✅ Синхронизация выполнена: создан commit и выполнен push» (если был коммит) или «✅ Синхронизация выполнена без нового коммита (pull --rebase → push)»; ниже — шаги и HEAD созданного коммита. Неудача: «❌ Синхронизация не завершена — см. упавший шаг ниже» и блок с «Путём исправления». Заголовок не исчезает, пока не начата новая операция. С 3.12.6 результат персистентен (state плагина Repos): панель восстанавливается после обновления страницы, под заголовком показывается время «последняя попытка: ДД.ММ.ГГГГ · ЧЧ:ММ (UTC+3)».
- При отсутствии локальных изменений кнопка «Перейти к подтверждению WRITE» не показывается — вместо неё «Продолжить без коммита (pull --rebase → push, потребуется подтверждение)».

### Прерванный rebase после конфликта pull --rebase (с 3.12.5)
- Если `pull --rebase` внутри Sync (или отдельный pull) остановился конфликтом, в разделе «Обзор» появляется янтарный баннер: rebase активен, перечислены конфликтные файлы.
- **Путь исправления**: разрешите конфликты в перечисленных файлах → нажмите «git add -A» в разделе «Изменения» → кнопка «rebase --continue» в баннере (активна, только когда конфликтов не осталось). Если продолжать не нужно — «rebase --abort» вернёт ветку в исходное состояние.
- `rebase --continue` с неразрешёнными конфликтами отклоняется бэкендом с честной ошибкой и «Путём исправления» — ничего не коммитится вполсилы.
- Проверка состояния — capability `repos.rebase_state` (READ/AUTO); продолжение/прерывание — `repos.rebase_continue` / `repos.rebase_abort` (WRITE/CONFIRM, требуется подтверждение).

### В разделе «Изменения» видны файлы, которые вы не меняли
- **Причина**: это не заглушка — раздел показывает все изменения того репозитория, чей путь открыт выше (карточка «Текущий проект»). Если в открытом репозитории лежат вложенные проекты (например, `G:\Mega\git` содержит папку drmPrintHelper), их правки отображаются общим списком.
- **Проверка**: сверьте путь в карточке «Текущий проект» (одинаков для Истории/Веток/Изменений).
- **Исправление** (если нужен другой проект): укажите в поле пути папку его репозитория (с `.git`) и нажмите «Открыть». Если файлы другого проекта должны быть отдельным репозиторием — сделайте их отдельным репозиторием и откройте его папку.

### «Действие … заблокировано: не выдано WRITE-разрешение …» (permission not granted)
- **Причина**: у плагина не выдано разрешение уровня WRITE. READ-разрешения (`repos.read`) выдаются автоматически при установке плагина, WRITE-разрешения (`repos.write`, `repos.sync`) — только вручную.
- **Исправление**: вкладка «Плагины» → раздел «Разрешения» → плагин «Репозитории» (repos) → выдать нужное разрешение (для Синхронизации — `repos.sync`) → повторить действие.
- **Код ошибки** в ответе API: `permission_denied`.

### «error: unsafe repository» / «detected dubious ownership in repository»
- **Причина**: папка репозитория принадлежит другому пользователю (например, каталог получен с другого диска/учётной записи, синхронизируется внешней программой), и git отказывается работать с ним.
- **Исправление** (запустить от того же пользователя, что и drmAIcu):
  - Windows (cmd/PowerShell): `git config --global --add safe.directory G:/Mega/git` (в кавычках — полный путь к папке репозитория, слэши допустимы);
  - Linux/macOS: `git config --global --add safe.directory /путь/к/репозиторию`.
  - Команда добавляет запись в список, а не заменяет его: посмотреть список — `git config --global --get-all safe.directory`. Если все репозитории лежат внутри одной общей папки, достаточно пометить её саму: `git config --global --add safe.directory G:/Mega`.

### «fatal: not a git repository …»
- **Причина**: указан путь, в котором (и выше по иерархии) нет папки `.git`.
- **Исправление**: указать полный путь именно к папке репозитория с `.git` (в интерфейсе путь должен начинаться с корня диска, например `G:\Mega\git`).

### «permission denied» / «Access is denied» при Синхронизации
- **Возможные причины и пути исправления**:
  - **git safe.directory** (см. раздел выше) — самая частая причина на Windows;
  - **нет прав на запись** в папку репозитория (каталог принадлежит другой учётной записи) — выдать права на папку в свойствах Windows или запустить drmAIcu от имени того же пользователя;
  - **антивирус/OneDrive/Mega-синхронизация** блокирует файлы `.git` — на время операции добавить папку в исключения либо приостановить стороннюю синхронизацию;
  - **файл заблокирован другой программой** (редактор, IDE держат файл открытым) — закрыть программы, работающие с репозиторием, и повторить.

### Backend недоступен / ошибки сети
- Вкладки плагина показывают «backend не доступен»: убедитесь, что drmAIcu запущен (start.bat), порт не занят другим процессом, и обновите страницу после перезапуска.

### Белый экран / оверлей Vite «Failed to resolve import "…"» после обновления
- **Причина**: новый PR добавил или обновил npm-зависимость (например, «Failed to resolve import "react-markdown" from "src/components/tabs/MDTab.tsx"»). Папка node_modules не хранится в git — после обычного `git pull` старые зависимости остаются на диске, а код уже ссылается на новые.
- **Исправление**: в папке проекта выполнить `npm install` и обновить страницу (Ctrl+R). Начиная с 3.11.1 это происходит автоматически: sync.bat ставит зависимости сам, если после pull изменился package-lock.json, а launcher.bat сверяет их при каждом старте.
- **Если npm install падает**: проверьте `node --version` и `npm --version`; при битом состоянии зависимостей удалите папку node_modules и файл package-lock.json, затем снова `npm install`.

### «Ошибка вспыхнула и мгновенно исчезла» (красная плашка при Синхронизации)
- **Причина (исправлено в 3.12.0)**: после синхронизации панель тихо перечитывает статус репозитория, и это перечитывание затирало только что показанную ошибку своим «репозиторий открыт».
- **Как теперь работает**: ошибка остаётся в красной плашке, пока вы сами её не закроете (клик по плашке); к узнаваемым git-ошибкам автоматически добавляется путь исправления.
- **Где искать историю ошибок**: вкладка «Логи» → кнопка «Ошибки и предупреждения (N)». Ошибки UI и ошибки плагинов пишутся туда автоматически и переживают перезагрузку страницы.

### Вкладка «Логи»: какие события туда попадают
- Лог ядра (запуск, патчи, перезапуски) — источники «Core»/«main.py»;
- Ошибки и предупреждения всех плагинов — источник «plugin/<id>» (читается из `data/plugins/activity/<id>.jsonl`, журнал плагина, ротация 2000 строк);
- Ошибки интерфейса (синхронизация, ветки, разрешения) — источник «Репозитории»/«Плагины»; отправляются на бэкенд (POST /api/logs) и не пропадают при перезагрузке страницы.
- Если вкладка «Логи» пустая при работающей панели — проверьте, что бэкенд запущен (откройте http://127.0.0.1:8000/api/logs — должен вернуться JSON с полем «logs»).
