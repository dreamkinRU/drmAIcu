# drmAIcu — История изменений

## v.3.7.0 Model (Текущая) — 26.11.2026

### Plugin System v1.0 + GitHub Plugin v1.0 (Этапы 0–1)

- **Plugin Manager** (`core/plugins/`) — реестр, лоадер (импорт как пакет `_plugin_<id>`, без записи в каталог плагина), жизненный цикл DISCOVER→…→UNINSTALL, изоляция ошибок (падение плагина не роняет ядро); реестр персистентен в `data/plugins/registry.json` и переживает рестарт.
- **Permission Manager** — уровни READ/WRITE/CRITICAL; выдача только заявленных в манифесте разрешений; при установке автоматически выдаются только READ; отзыв блокирует вызовы немедленно.
- **Capability Gateway + подтверждения** — операции плагинов выполняются только через `POST /api/plugins/{id}/exec`; auto-READ выполняется сразу, WRITE/CRITICAL создают одноразовое подтверждение (TTL 15 мин, повторное использование отклоняется, mismatch параметров отклоняется).
- **Secret Manager** — секреты per-plugin в `data/plugins/secrets/` (0600 best-effort), никогда не возвращаются API; журнал активности redact'ит известные значения секретов (`***REDACTED***`).
- **REST `/api/plugins/*`** — единый формат `{success, error, code}`; монтирование в `main.py` — 2 строки.
- **GitHub Plugin v1.0** — манифест (15 разрешений), GitHub App: JWT RS256 → Installation Access Token с кэшем и refresh по 401, диагностика подключения; capabilities: test_connection, repositories, tree/file, branches, compare, create_branch (WRITE → подтверждение); Git CLI через allowlist (`git_service.py`, shell=False, таймауты).
- **Frontend** — вкладка «Плагины»: Установленные / Каталог / Разрешения / Активность + панель ожидающих подтверждений (approve/reject).
- **Безопасность** — `guards.CRIT_DIRS` расширена (`core/`, `plugins/`, `data/plugins/`): cleanup не может удалять код плагинов и секреты; `data/plugins/` добавлен в `.gitignore`.
- **Контракты** — `docs/PLUGIN_SYSTEM.md`, `docs/PLUGIN_API_CONTRACT.md` (манифест, жизненный цикл, политики подтверждений, границы доверия v1.0).

Тесты: +48 (`tests/test_plugins.py`, `tests/test_github_plugin.py`, `tests/test_plugins_api.py`: жизненный цикл, права/отзыв, одноразовые подтверждения, redact секретов, изоляция ошибок, путь-траверсал архивов, REST-контракт) — всего 187, все зелёные; `tsc --noEmit` и `vite build` — зелёные.

### Транзакции патчей: целостность откатов и crash-восстановление (B48–B52)

Исправлено (находки уровня P1 в Patch Engine):
- **B48 (P1-01) — rollback уничтожал пользовательские правки**: перед откатом текущий файл сверяется с checksum применённого патча из манифеста; если файл изменён после применения (или исчез), откат останавливается с явным сообщением и правки не теряются
- **B49 (P1-02) — rollback стал двухфазным**: сначала ВСЕ восстанавливаемые файлы готовятся во временных `.rbk.tmp`-копиях с проверкой контрольных сумм, только затем контролируемая замена; сбой оставляет журнал и состояние, пригодное для повторного отката, а не частично откаченный проект
- **B50 (P1-03) — частичный откат больше не выдаётся за удачный**: если автооткат после ошибки apply восстановил не всё, ответ содержит `rollback_failed` со списком файлов, `rollback_incomplete: true` и предупреждение в error; журнал `patch_journal.json` сохраняется для последующего восстановления
- **B51 (P1-04) — crash-журнал транзакций**: применяется/откатывается по шагам с журналом `patch_journal.json` (tmp + fsync + атомарная замена); при аварийном завершении процесса между файлами после перезапуска `_pe.recover_journal()` на старте `main.py` достраивает транзакцию; в `stats()` появилось поле `locked`

### Оборона производителя патчей: волна 3 — тампер-детект, дубликаты, строгий diff

#### Исправлено (все — реальные дефекты, вскрытые новыми тестами)
- **B40 — подменённый бэкап не обнаруживался при откате**: rollback восстанавливал содержимое из `backups` без сверки с манифестом — злоумышленник (или сбой диска), переписавший `.bak`, подсовывал под откат произвольный контент. Теперь rollback работает по схеме verify-first: в манифесте фиксируется `backup_sha` (sha контента ДО apply), и ВСЯ целостность (safe_path, существование, контрольная сумма) проверяется ДО первой записи на диск. Несовпадение → откат отказывает, файл не тронут, запись в манифесте не снята
- **B43 — повторное применение патча не отвергалось**: apply того же `patch_id` дважды дублировал записи в манифесте и портил цепочку откатов. Теперь повторное применение отвергается по `applied`; после rollback (где запись снята с `applied`) переприменение разрешено — это штатный путь «накат → откат → накат»
- **B44 — `apply_diff` молча принимал мусор**: пустой diff, текст без валидных `@@`-ханков и ханки без единой строки `-`/`+` проходили и (в зависимости от кода) делали пустые записи в манифесте. Теперь все три случая вызывают понятный `ValueError` ещё до транзакции

#### Добавлено (тесты, 81 → 88)
- **B40** (`test_engine.py`): подмена файла бэкапа → откат отказывает с ясно указанной причиной, целевой файл не тронут, запись не снята; нетронутый бэкап → откат проходит штатно
- **B40b**: полный apply→rollback при включённом `backup_sha` — обратная совместимость
- **B41** (`test_patching_hardcore.py`, `TestMidTransactionDefense`): create-цель появилась между `compute_ops` и транзакцией → отказ «появился во время транзакции», чужой файл не тронут, манифест пуст
- **B42**: диск заполнился (OSError 28) при записи tmp второго файла → полный откат (create-файлы удалены), манифест пуст, `*.tmp` не осталось
